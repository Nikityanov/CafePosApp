# OpenCode Agent Rules

CafePosApp — .NET MAUI 10 point-of-sale app for a coffee shop. Targets Android (primary
device), iOS, MacCatalyst and Windows. Russian-language UI, Material 3 styling, SQLite
via EF Core, fully offline.

**This file is tracked in git.** It was ignored until 2026-10-07, on the theory that the
rules were machine-specific. That was wrong: a rule that cannot be reviewed, diffed or
rolled back is indistinguishable from no rule, and §17's write-back obligation needs
somewhere to land. A rule change is now an ordinary commit, reviewed like any other.

---

## 0. Skills are installed — use them instead of improvising

41 .NET/MAUI agent skills from the official `dotnet/skills` repo (Microsoft .NET team)
are installed globally in `~/.config/opencode/skills`. They are model-invoked: reach
for one by name whenever the task matches its trigger, rather than reasoning from
memory about an API you can look up.

**Load the skill, then act.** Invoking a skill is cheap; a wrong guess about a MAUI
API is not — see §1.1.

| Task | Skill |
|---|---|
| Any XAML / binding change, `x:DataType`, XC0022 / XC0025 | `maui-data-binding` |
| Lists, grids, item templates, recycling, swipe actions | `maui-collectionview` |
| `GoToAsync`, routes, flyout, navigation guards | `maui-shell-navigation` |
| `MauiProgram.cs` registration, lifetimes, testability | `maui-dependency-injection` |
| Edge-to-edge, notch, keyboard, status bar overlap | `maui-safe-area` |
| Light/dark, `AppThemeBinding`, `ResourceDictionary` | `maui-theming` |
| `OnAppearing` / `OnDisappearing`, backgrounding, resume | `maui-app-lifecycle` |
| SDK / JDK / Android SDK / workload errors, setup | `dotnet-maui-doctor` |
| Slow EF Core query, too many round-trips, N+1 | `optimizing-ef-core-queries` |
| Any `dotnet test` invocation, filters, TRX, coverage | `run-tests` |
| Writing new unit tests for Core | `code-testing-agent` |
| "Would these tests catch a bug?" | `test-gap-analysis` |
| Audit / smell / assertion review of a test suite | `test-anti-patterns`, `assertion-quality`, `test-gap-analysis` |
| Performance audit, allocation-heavy paths | `analyzing-dotnet-performance` |
| Native crash on device (`.ips` or tombstone) | `apple-crash-symbolication`, `android-tombstone-symbolication` |
| Rename / extract / move / consolidate C# members | `csharp-refactoring` |
| **Before any new feature or fix — mandatory** | **`grill-me`** → §17 |
| Turning a decision into steps | `planning-with-users`, `writing-plans` → §17 |
| Reducing or explaining a hard design choice | `simplify`, `grill-me` |
| Reviewing my own work before the user sees it | `verification-planning`, `coverage-analysis` |

Two rules about the boundary:

- **Skills give the general rule; this file records our specific incidents.** A skill
  may say "prefer X"; §2 says which trap X caused *here* and what to do about it. When
  they conflict, this file wins — it is paid for with real crashes.
- **A skill is not a substitute for measurement.** Per §1.2, layout still ships with a
  screenshot or a measurement, whatever the skill recommends.
- **A skill that produces a decision obliges you to write that decision back into this
  file.** `grill-me` and the planning skills are how we decide things; §17 is how what we
  decided stops being lost. Reach for the skill, then honour the write-back — the two are
  one step, not two.

**Deliberately not installed / not relevant:** `create-datadriven-aspnetcore` (no
ASP.NET here), `clr-activation-debugging` (.NET Framework, not .NET 10),
`writing-mstest-tests` and `scaffold-dotnet-test-project` (we are on xunit). They are
inert — their descriptions carry explicit `DO NOT USE FOR` triggers.

## 1. Verification comes first

This is the highest-value section. Most of it is here because the alternative was
already paid for.

### 1.1 A Debug build verifies almost nothing about XAML

`dotnet build -c Debug` compiles but parses XAML **at runtime**. A Release build runs
XamlC, which rejects at compile time what Debug accepts and only fails later, at
inflation, in front of the user.

- **After ANY change to a `.xaml` file, run a Release build.** Not just Debug.
  `dotnet build CafePosApp.csproj -f net10.0-windows10.0.19041.0 -c Release`
- If Release does not build, the change is not done — regardless of Debug being green
  and the screen looking right.
- **Every XAML file declares `x:DataType`.** Without it, binding paths are unverified
  strings: a typo is silent, and XamlC emits an XC0022 warning per binding. With it,
  binding paths are checked at compile time. → `maui-data-binding`
- Never name a property, element or event you have not verified exists in MAUI 10.
  In Debug, an unknown member is a **process abort at inflation**, not a build error.
  → `maui-data-binding`, and check the API against Context7, not against memory.
- **Never guess an enum value in XAML.** This is a separate, sharper failure than an unknown
  member: the *property* exists, so both a Debug and a Release build stay green, and the
  process then dies at inflation with `ArgumentException: Requested value 'X' was not found`.
  Three were hit in one session, and all three builds were clean:
  - `VerticalTextAlignment="Top"` — it is `LayoutAlignment` (Fill/Start/Center/End); `Top`
    belongs to `TextAlignment`
  - `HorizontalScrollBarVisibility="Visible"` and `="Auto"` — `Microsoft.Maui.ScrollBarVisibility`
    has exactly **Default, Always, Never**
  - Get the members, do not recall them. Read the enum off the shipped assembly
    (`obj/…/android/assets/x86_64/Microsoft.Maui*.dll` via `dotnet script` + `Enum.GetNames`)
    or the docs. There is no build-time safety net, so the only check is running the app —
    which is why §1.1's Release build is necessary but **not sufficient**.

Predicting a layout from reading XAML does not work. Three consecutive rounds of
predicted widths were all wrong; every one was caught only by a real screenshot or a
runtime measurement.

- Any layout or responsive change ships with a **measurement or a screenshot**, never
  with a calculation.
- `CatalogManagementPage` has a one-shot `[LayoutDiag]` diagnostic that logs the real
  widths/heights and warns on overflow. Use it rather than predicting.
- If a measurement cannot be taken, say so explicitly. Never present a prediction as a
  measured fact.
- **Maestro MCP can take that measurement for you** — see §10. Prefer it over asking
  the user to send a screenshot.

### 1.2 How to take the measurement, concretely

Reading `wm density`, dumping the view hierarchy and looking at a cropped screenshot is
how every layout claim in this file got verified. Do it this way rather than estimating.

**Get the scale first.** `adb shell wm density` returns dpi; the scale factor is
`density / 160`. The emulator is **420 dpi → 2.625**, so 1080 px is 411 dp wide and
`dp = px / 2.625`. Every number below is in those units.

**Read real bounds, not a screenshot.** `uiautomator dump` gives the platform's own view
of what is on screen, in pixels, which converts to dp exactly:

```
adb shell uiautomator dump /sdcard/ui.xml
adb pull /sdcard/ui.xml "$env:TEMP\ui.xml"
```

Each node carries `bounds="[x1,y1][x2,y2]"`. Parse the attribute and divide. This is how
the chip defect was pinned down: the label node came out **57×66 px = 21.7×25.1 dp**,
where a single line of 13 pt text is ~16 dp tall — so the text was on two lines, and the
surrounding border was 25 dp instead of the 44 the style asked for. A screenshot alone
shows "it looks wrong"; the dump says why.

**Look at the screenshot too, and crop it.** A 1 dp stroke is invisible at 1×. Crop the
region and scale it 2–3× with `System.Drawing` before reading it — the malformed pills
were obvious the moment they were enlarged, and completely ambiguous at full size.

```
adb exec-out screencap -p > "$env:TEMP\shot.png"
```

Then crop + `InterpolationMode.NearestNeighbor` + upscale. **Actually read the image with
the image tool.** Capturing it is not looking at it.

**Find things by dumping, never by remembering coordinates.** Nav tab centres, the FAB,
the stepper `+`/`−` — all of them come out of `bounds`, and all of them have changed
between sessions. Guessing a tap coordinate silently hits the wrong control or misses and
looks like a dead button.

**Three text traps in this workflow:**

- **Never verify Russian or any non-ASCII text by reading console output.** The PowerShell
  console renders it as mojibake regardless of the file being correct. Print
  **codepoints** (`'{0:X4}' -f [int]$char`) or re-read the file with the read tool. An
  entire debugging session was spent on text that was already fine.
- Launch with
  `adb shell monkey -p com.companyname.cafeposapp -c android.intent.category.LAUNCHER 1`.
  `am start -n` **fails** — `MainActivity` sits under a generated namespace.
- Exceptions are in the file, not logcat: §10.5.

**The Debug APK path is `bin\Debug\net10.0-android\`,** not `bin\android\Debug\`. Install
with `-r` to keep the database; cart and catalogue survive.

### 1.3 Independent verification of delegated work

- Verify subagent output by reading the actual files and re-running the checks. Do not
  accept a report as evidence. Three defects shipped in a "complete and verified"
  report: a detached FAB, an input-swallowing overlay, and changes that were described
  but net-zero against HEAD.
- Correct the subagent, not just the symptom. When a defect is found, ask what class of
  mistake produced it.

## 2. MAUI platform traps

Each of these has already caused a real defect or crash in this codebase. The long
explanatory comments in the source files record the incidents; this is the index.

| Trap | Rule |
|---|---|
| Debug parses XAML at runtime | Unknown member = process abort. Verify against docs, not against a green build. → `maui-data-binding` |
| Transparent overlay sized to its cell | A `ContentView` with no `HorizontalOptions` defaults to `LayoutOptions.Fill` and covers the whole cell. It swallows touches on iOS, where a transparent `UIView` still hit-tests. Size overlays to their content. |
| `LayoutOptions.Fill` vs explicit size | An explicit `WidthRequest`/`MaximumWidthRequest` **wins** over `Fill`, and the element is centred. Never combine `Fill` with an `Auto` parent column and expect the parent to contain it. |
| `Auto` parent + `Fill` child | Contradiction: the child demands all space, the parent sizes to the child's desire. The child grows past the window and star columns collapse to zero. |
| `CollectionView` inside a `ScrollView` | Defeats recycling. Never nest. → `maui-collectionview` |
| `RefreshView` over a Grid of lists | Cannot pull on Android, and cannot stop its own spinner (dotnet/maui#12469). Refresh stays a real button. → `maui-collectionview` |
| Long press | MAUI ships none. Use CommunityToolkit `TouchBehavior`. `ShouldCaptureTaps` no longer exists. → `maui-collectionview` |
| `OnSizeAllocated` on a Shell page | Never fires; the page's own `Width` stays 0. Use `Application.Current.Windows[0].Width`. → `maui-app-lifecycle` |
| `ItemsLayout` binding context | A `BindableObject` outside the visual tree; `{Binding}` on `Span` does not reliably inherit the page's. Assign from code. → `maui-collectionview` |
| `FlexLayout` spacing | No `Spacing`/`RowSpacing`/`ColumnSpacing` at all. Use a Margin per child. |
| `FlexLayout` and `HeightRequest` | **`FlexLayout` does not honour a child's `HeightRequest`.** Measured: chips asking for 44 dp came out 25 dp, and a 1 dp `RoundRectangle 22` stroke on a box that short drew only its corner arcs — the chip looked like two loose curves with the label jammed between them. **`HorizontalStackLayout` measures children properly and honours `HeightRequest`**, and it has the `Spacing` that FlexLayout lacks. Any horizontal chip strip: `ScrollView Orientation="Horizontal"` > `HorizontalStackLayout Spacing="6"`. → §13 |
| `MaxLines` on a `Button` | `Button` has **no `MaxLines`** — XamlC `XC0001: Cannot resolve property`. It is a `Label` property. `Button` *does* take `LineBreakMode`. A chip whose text wraps is what pushes a tab off the screen edge. |
| `ScrollView` scrollbar visibility | `Microsoft.Maui.ScrollBarVisibility` has exactly **Default, Always, Never** — §1.1. And `Default` showed **no bar at all** on Android in a screenshot taken right after a swipe, so it is not a reliable "scroll me" cue. |
| `Button.Content` / `ControlTemplate` | `Button` is text-and-image only. Marks are siblings of the button, not its content. |
| `ContentTemplate` | Only on `ShellContent` and WinUI platform types. Not on `ContentView`, `ContentPage`, `ContentPresenter`. → `maui-shell-navigation` |
| `Path.Data` bound to a string | `Data` is a `Geometry`; a string from a binding throws `InvalidCastException`. Use a literal attribute. |
| Page lifecycle | Pushing a modal raises `OnDisappearing` on the page underneath. Subscribe in `OnAppearing`, unsubscribe in `OnDisappearing`, symmetrically, with `-=` before `+=`. An asymmetric pair silently kills event-driven UI after one open. → `maui-app-lifecycle` |
| Content under the notch / status bar | Edge-to-edge is default on .NET 10. Use `SafeAreaEdges` / `UseSafeArea`; do not hand-roll padding. → `maui-safe-area` |
| `ColumnSpan` on a `View` | It is a **`Layout`** property. On a `Label` it throws `XamlParseException` the moment the first row of a `DataTemplate` is realised — i.e. inside the load, where a page-level `catch` turns it into "не удалось загрузить" sitting under figures that already updated. Use nested layouts instead. → `maui-data-binding` |
| `RelativeSource AncestorType={vm:SomeViewModel}` | Makes the XAML runtime try to **instantiate** that type. Every ViewModel here comes from DI, so it is an `XamlParseException`. Working idiom: `x:Name` on the root `ContentPage` + `Source={x:Reference Name}, Path=BindingContext.Command`. 39 sites use it — read §8 before changing it. → `maui-data-binding` |
| `BindableLayout` fed a `SetItem` | `ReplaceChild` is the **only** one of MAUI's five handlers that does not re-establish the item↔child correspondence; it indexes `layout.Children[e.OldStartingIndex]` and throws `ArgumentOutOfRangeException`. Add/Move/Remove/Reset all go through `e.Apply(...)` and cannot produce that shape — so `Replace` is the canary, not the root cause. Never let a `BindableLayout` list raise `SetItem`. Realised children are also **not** reset on detach: a page that left the screen keeps updating and nothing rebuilds on return, which makes the failure intermittent and dependent on how many times the page was entered. → `maui-collectionview` |
| `e.Cancel()` | A method group, not an assignable property. |
| Converter resource names | In `App.xaml` they are `InvertedBoolConverter` and `IsPresent`. Not `Invert`, not `StringNotEmpty`. |
| `GoToAsync` on a global route | A route registered with `Routing.RegisterRoute` does a **push onto the stack of whichever tab is current**; switching tab with `///tab` does not remove it. Pop first, then switch — `await GoToAsync("..")`, then `await GoToAsync("///menu")`. Skipping the pop leaves a screen claiming "no shift is open" on top of a shift that has been open for a minute. → `maui-shell-navigation` |
| Long `DisplayAlert` message | Android drops the buttons out of their side-by-side row and renders them as **borderless text buttons, stacked and right-aligned**. On the shift page that stripped the chrome off the *most destructive* confirmation in the app. Keep destructive confirmations short, and do not put free-text fields in them. |
| The overflow tab's label | Not a `ShellContent.Title`, and not settable from C#. Android reads the string resource `overflow_tab_title`, which an app-level `Platforms/Android/Resources/values/strings.xml` overrides at merge time — the same mechanism this project already uses for `Maui.SplashTheme`. Read that file before proposing to restructure the tab bar; the alternatives are all worse. → `maui-shell-navigation` |

## 3. Git: one branch per feature, then merge into `develop`

`develop` is the single integration branch. **Every feature or fix gets its own branch,
off `develop`, and is merged back into `develop` when it is done.** This is the rule, and
it is written with commands because the principle alone did not survive: a whole session of
completed, verified work was committed straight onto `develop` with no branches at all.

### 3.1 Start

```
git switch develop
git pull
git switch -c fix/catalog-chip-strips          # or feat/…, refactor/…, docs/…, chore/…
```

- **Branch naming: `feat/…`, `fix/…`, `refactor/…`, `docs/…`, `chore/…`** — lowercase,
  hyphens, and the subject after the slash (`fix/catalog-form-button-dead`).
- **Never commit to `develop` directly.** Not for a "quick" fix, not because the branch
  feels like overhead, not because the work is one file. The branch is what makes the
  change reviewable and revertible as a unit; §16's change record is only meaningful
  against one.
- **Branch off `develop`, never off `master`.** `master` is not a working branch;
  releases are cut from `develop`.
- **Open the change record (§16) in the same commit as the first code change**, on the
  branch. A record written after the fact is a description, not a record.

### 3.2 During

- **One commit, one concern.** Never mix unrelated work into one commit — a large
  pre-existing changeset once got bundled with a focused fix and became unreviewable.
- Conventional subjects, which is the de facto style here: `fix:`, `feat:`, `refactor:`,
  `docs:`, `test:`, `chore:`. The subject says what changed; the body says why and how it
  was verified.
- **Push the branch as you go** so the work is reviewable on GitHub before it lands:
  `git push -u origin fix/catalog-chip-strips`
- Never rewrite published history without explicit instruction.

### 3.3 Merge, then delete the branch — in the same sitting

**A feature branch is deleted the moment it is merged. Both copies: local and remote.**
This is not tidiness; §3.5 is what happens when it is skipped.

1. `dotnet build … -c Release` is clean. Debug is not enough for XAML (§1.1).
2. `dotnet test` is green, with **no expectation edits** to make it pass.
3. The layout/visual work has a **measurement or a screenshot** on the device (§1.2).
4. **The owner has confirmed it works.** An untested merge is not a merge. The agent's own
   emulator pass (§4) satisfies items 1–3; it does **not** satisfy this one. Item 4 is the
   owner's, and it is the only item no amount of automation substitutes for.
5. The change record (§16) is complete, including the numbers, and `.opencode-rules.md`
   carries anything new this work decided (§17).

```
git switch develop
git pull
git merge --no-ff fix/catalog-chip-strips      # --no-ff keeps the feature's commits visible
git push origin develop
git branch -d fix/catalog-chip-strips          # local
git push origin --delete fix/catalog-chip-strips   # remote — the one that actually piles up
```

- **`--no-ff`, not squash and not fast-forward.** The merge commit is the index entry for
  the change record; squashing would erase the boundary the record describes. It also
  makes `git log --oneline --graph` show exactly what each feature was.
- **`develop` branches the next feature.** One feature at a time; a second branch off
  `develop` before the first is merged means two unrelated changes in one merge.

### 3.4 Delete, and do not ask permission to delete

`git branch -d` is refused by git if the branch is unmerged, which is the safety property
we want. Once the merge commit exists, deleting the branch **destroys nothing**: every
commit is reachable from `develop`, and the change record (§16) still names the work. A
merged branch kept "just in case" is keeping something that cannot be lost.

- **After every merge, without being asked.** It is step 6 of the merge, not a favour.
- **`git branch -d`, never `-D`.** If `-d` refuses, the branch is genuinely unmerged —
  stop and ask the owner, do not force it.
- **`master` is never deleted**, and neither is `develop`. A branch the owner is still
  working on is not deleted.
- **Six stale branches were found on 2026-10-07** — four `feat/`, one `fix/`, one `chore/`,
  all merged, all still on the remote. They cost nothing but they make `git branch -a`
  unreadable, and they hide the one branch that did still matter.

### 3.5 Why this is not optional: an unmerged branch rots

`fix/analytics-scrolling` was branched on **2026-10-01** and never merged. It carries real
work — "the product breakdown on Аналитика showed three rows of a four-row list", 68
insertions across a ViewModel and its page. Six days later `ShiftAnalyticsViewModel.cs` was
refactored into eight files, and the branch **now conflicts with `develop`**:

```
git merge-tree --write-tree develop fix/analytics-scrolling
  → CONFLICTS: ViewModels/ShiftAnalyticsViewModel.cs, Views/ShiftAnalyticsPage.xaml
```

Its cost did not arrive when it was written; it arrived when the files around it moved.
**An unmerged branch gets more expensive every day, and the price is paid by the next
change rather than by the one that caused it.** Merge it, or abandon it on purpose — do not
leave it to rot. A branch nobody intends to finish should be deleted in the same sitting,
and its change record set to `Status: abandoned` with the reason.

### 3.6 Housekeeping, occasionally

Before starting something new, look at what is left:

```
git branch --merged develop        # safe to delete
git branch --no-merged develop     # needs a decision: merge, or abandon on purpose
git branch -r --no-merged origin/develop
```

Anything in the first list is clutter. Anything in the second is a decision someone has not
made yet, and it should be surfaced to the owner rather than silently tolerated.

## 4. Build policy

Split by cost and by who is better placed to run it.

- **Compilation checks are encouraged** — run `dotnet build` and `dotnet test` freely.
  They are cheap and catch real defects (a broken Release build went unnoticed for an
  entire session of Debug-only work). Do not ask permission for these.
  - Debug + Windows target for a fast check:
    `dotnet build CafePosApp.csproj -f net10.0-windows10.0.19041.0 -c Debug`
  - **Release after any XAML change** (see §1.1) — this is not optional.
  - `dotnet test Tests/CafePos.Tests.csproj -c Debug` must stay green (490 tests).
    Use the `run-tests` skill for the exact command rather than reconstructing flags.
- **The emulator is the agent's to drive.** Deploy, launch, screenshot, measure and tap on
  `emulator-5554` without asking — the owner has authorised exactly this, and §1.2 exists
  to make it easy. Verification that is skipped is verification that did not happen.
- **The physical phone stays the owner's** — §10.1. Never `clearState`, never uninstall,
  never write to that database, unless authorised for that specific action.
- Report changes clearly enough that the owner can build and verify without re-reading
  the diff — and say plainly what was measured versus what was predicted.

## 5. Domain invariants — do not break these

- **Money is integer kopecks at rest.** SQLite stores decimals as TEXT, which breaks
  `SUM`/`ORDER BY`/comparisons and is unsupported by decimal aggregates. The domain
  exposes `decimal` through `Money`. Never introduce `double` or `float` for money.
- **User-facing money goes through `TextFormat.Money` only.** `Money.FromKopecks` is
  for converting into the domain, never for markup — it produces a raw two-decimal
  form that ignores the operator's selected currency. The same applies to plurals:
  `TextFormat.Plural(count, one, few, many)`. Hand-assembling either in markup has
  already produced `"1 товаров"` in one file and `"1 заказов"` in another; both helpers
  exist precisely so the rule lives in one place.
- **Products are soft-deleted.** `IsDeleted` + `DeletedAt`. A deleted product leaves
  the menu but stays in order history. Hard delete breaks past orders.
- **Russian UI, one plural implementation.** Use the shared `Plural(one, few, many)`
  helper. Never write `"1 товаров"` into markup.
- **A null category is a first-class state**, rendered as an explicit "— Без раздела —"
  row and a hidden pill, never as an empty box.
- **SQLite cannot `ORDER BY` a `DateTimeOffset`** — it throws `NotSupportedException`
  rather than sorting silently. Anything ordered by a stored timestamp has to be sorted
  in memory over an already-materialised projection; the shift list, the last counted
  cash and the movement list each do this.

## 6. Product rules (POS)

The phone is the primary device; tablet and desktop are targets, not the reference.

- **Touch targets: state the floor in MILLIMETRES, then convert to dp for the screen.**
  A dp threshold alone is not a physical-size rule — it is a *different* physical size on every
  density, and it fails silently because nothing about the layout looks wrong. **The two numbers
  must be checked together, and the millimetres are the ones that decide.**

  | density | 48dp is | the 9–10 mm a 7–11″ tablet wants is |
  |---|---|---|
  | 420 (`wm density` on the emulator) | **126px = 7.6 mm** | **57–63dp** |
  | 320 (a 360dp phone) | 96px = **7.6 mm** | 57–63dp |

  - 48dp is the **default floor**, and it is **under** the ergonomic minimum on a counter tablet. If
    a layout cannot hold 48dp, the layout is what has to give — delete a row, merge two controls
    into one, or collapse a disclosure.
  - **To make space, delete elements.** A request to "shrink the buttons" is usually a request for
    less on screen, and it is the wrong instrument: Bachynskyi (CHI 2015) measured muscle activation
    on a vertically-positioned public display at **45% worse than average**, and a counter tablet is
    exactly that surface. Compacting by deleting rows is the fix; compacting by shrinking targets
    trades a layout problem for a musculoskeletal one.
  - **KNOWN EXCEPTIONS — the owner may overrule this, and a rule the code silently violates is
    worse than a small control.** Each one below is a decision, not an oversight, and each is
    recorded at the control as well.
    - **The cart `+`/`−` stepper is 40dp** (105px, 6.3 mm at 420dpi), not 48dp. The owner decided it
      after the 48dp argument was made and overruled, because two steppers flanking the quantity
      spent 96dp of a 411dp row on two glyphs while the dish name and price were compressed. Those
      two labels were raised 13sp → 15sp at the same time. See the stepper comment in `MenuPage.xaml`.
    - The chip strip uses 44dp, one notch under the default and still a whole chip.
  - This is not a hypothetical on this app: the owner twice asked for cart controls to shrink. The
    first time the answer was to delete the «Итого» row, one checkout button and one fulfilment
    segment instead, and that is where the space came from. The second time the stepper itself was
    the thing that had to give, and it did — the row was not deleted instead, because by then there
    was nothing left on the row to delete.
- **XAML `clr-namespace:` without `;assembly=` resolves in the assembly of the XAML file itself.**
  The omission is free until the type MOVES to another assembly, and then it is a launch crash:
  `XamlParseException: Type OrderTab not found in xmlns clr-namespace:…` — at runtime, with a clean
  build and every test green. It cost a day when the ViewModels became `CafePos.Presentation`: all
  13 XAML files had been correct while those types lived in the MAUI project, and every one of
  them was wrong the moment they moved. **Any `clr-namespace:` naming a namespace that is not in
  this assembly needs `;assembly=`.**

- **A ViewModel holding a MAUI type cannot leave the MAUI project — and the type is rarely the
  one you would guess.** `Color` is fine: `Microsoft.Maui.Graphics` is a graphics assembly that
  builds and runs on plain net10.0 (verified with a throw-away project, not assumed).
  `Application.Current.Resources`, `AppTheme`, `MainThread`, `Geometry` and `Preferences` are
  not. Measure which before designing the seam — a "tone" abstraction replacing every colour
  would have been 35 edits solving a problem that does not exist, while the real blocker was one
  call to `Application.Current.Resources`.

- **A `Picker` never shares a row with another control on Android — it steals its touches.**
  The Spinner that backs a MAUI `Picker` is measured **wider than its `*` grid column**, and its native
  touch target spills across whatever sits to its right. The controls it covers still draw perfectly, sit
  at exactly the right coordinates, and never once answer a press — so it reads as a dead command or a
  wrong binding, and no amount of inspecting the command will find it. Measured on this app: in the combo
  slot, the stepper's `+` was dead while the `×` one column further right worked on every press. Removing
  the `Picker` made `+` live immediately (1 → 2, «по отдельности» 660 → 820), which is what identified it.

  **Give the `Picker` a row of its own, at full width.** In `CatalogFormsPage.xaml` the combo slot is two
  lines for this reason — dish above, contribution + stepper + `×` below — and that is not the layout one
  would draw from scratch. When a control in a `*` column is mysteriously untappable, suspect its left
  neighbour before suspecting its own binding.
- **Price is the most-scanned value on a product row** and must be the most prominent
  thing on it. If price and name compete, price wins.
- **A destructive action is always confirmed**, and a permanently armed destructive
  input is never left on screen.
- **Feedback is never colour-only** — pair colour with an icon or with wording.
- **Densities matter**: an 85dp row shows 8 products where a 50dp row shows 12. Prefer
  compact rows to scrolling.
- Show unavailable items as a **state**, not as an action; the action lives in the
  overflow menu.

## 7. Testing, and its honest limit

- `Core` (126 files) is well covered by unit tests. `Tests` has 490 tests over domain
  logic: money, catalogue, checkout, drafts, migrations, text formatting, the cash
  ledger and its corrections, shift reconciliation, the close-count prefill, and the
  collection-sync invariant.
  → When adding coverage, use `code-testing-agent` to design cases. When asked whether
  the suite would actually catch a regression, use `test-gap-analysis` (pseudo-mutation:
  it reasons about *which* production change would slip through) — not a coverage
  percentage, which says nothing about that.
- The application layer (`Views` 18, `Controls` 4, `Converters` 7, `Services` 17, plus
  `CafePos.Presentation` 70) has **no automated coverage**, and this is structural, not
  an oversight: `Tests` does not reference the MAUI project at all, so it *cannot* see
  it — see §12.
- **What unit tests cannot cover here:** MAUI page lifecycle, layout and responsive
  behaviour, platform hit-testing, and anything Debug-only XAML lets through. These are
  verified by a Release build (§1.1) plus a manual pass on a real device.
- A native crash on device is not debuggable from the log alone. If `AppLog` shows a
  native abort rather than a managed exception, use `android-tombstone-symbolication`
  or `apple-crash-symbolication` to resolve the frames to real method names.
- Prefer pushing decisions into `Core`, where they become testable, instead of burying
  them in a ViewModel.
- The comments record real crashes and are load-bearing. **Update the ones your change
  invalidates; never delete one.** But note what "long" means now: a comment is no longer
  kept in the file at length — the reasoning lives in `docs/decisions/` and the code keeps
  a pointer, per §11. Moving text is not deleting it, and §11 is where the boundary is.

## 9. What the C# language server does and does not cover

OpenCode has the built-in `csharp` LSP server enabled (`"lsp": true` in
`~/.config/opencode/opencode.json`, `csharp-ls` 0.28.0 installed globally). It starts
on the first `.cs` file opened and feeds Roslyn diagnostics back into the agent loop.

- **Use it for:** unresolved symbols, wrong argument counts, nullable warnings, missing
  `using`, type mismatches. These are caught before a build is run.
- **It does NOT cover XAML.** No LSP reads `.xaml`. Compiled bindings, `x:DataType`
  mismatches and XamlC errors are invisible to it — §1.1's Release build remains the
  only thing that verifies them.
- **It does NOT model the `Core` project boundary.** The main csproj excludes
  `Core\**` from its compile globs, so a type added to `CafePos.Core` and referenced
  from the app can be flagged as unresolved by the app-project server while
  `dotnet build` is green. Treat a lone "not found" on a `Core` type as likely noise
  and confirm with a build before "fixing" it.
- Diagnostics are advisory, not a gate. A green build plus green tests still outrank a
  quiet LSP.

## 10. Maestro MCP — eyes on the emulator

Maestro 2.11.0 is installed with its MCP server (`maestro` in `opencode.json`). It gives
the agent `inspect_screen`, `take_screenshot` and `run` against a device. This is how
§1.2 gets satisfied without asking the user for a screenshot. Setup, commands and the
verified smoke flow are in `maestro/README.md`.

### 10.1 Never touch the physical device

A real POS terminal, Samsung SM-S916U1, is attached as `R3CWA03SDKN`. It holds a
working local database.

- **Always pass `device_id: "emulator-5554"`.** Never `R3CWA03SDKN` by default.
- `launchApp` with `clearState: true` wipes app data. On that terminal that is the
  operator's menu, stock and order history.
- `list_devices` returns both. The choice is manual and there is no safe default.
- If the emulator is down, **ask** — do not fall back to the phone.
- **The user can authorise the phone explicitly, and has.** Installing a build there is
  then fine, and `adb -s R3CWA03SDKN install -r -t` preserves the database — that is how
  the cash-operations build reached the real 360dp device with the operator's catalogue
  and an open shift intact. What stays prohibited without that authorisation is anything
  **destructive**: `clearState`, uninstalling, or writing to the database.
- The terminal may carry a `wm density` override, which changes its effective width
  without changing the phone. Check `wm density` before reasoning about layout there —
  480 means 360dp, not the 384dp its physical density implies.

### 10.2 The emulator needs minutes, not seconds

It takes 3–5 minutes to become usable. `boot_completed=1` arrives while the system is
still settling; `uptime` can still show a load average near 40.

- After boot, check `adb -e shell uptime`. Proceed when the load is under 20.
- A flow started too early runs partway and then fails somewhere unrelated. That is an
  emulator artefact, not an application defect — do not "fix" the app for it.
- **To check narrow layout without the phone**, override the density rather than hunting
  for a device: `adb -e shell wm density 480` makes a 1080px-wide screen 360dp
  (1080 / (480/160)), and `adb -e shell wm density reset` puts it back. This is the only
  way most 360dp defects showed up here, and none of them were visible at 411.
- A **first app start takes ~8 seconds** (schema + seed + automatic backup) and shows a
  blank screen throughout. Wait for the UI, do not diagnose it as a hang.
- **Neither the density change nor a failed start kills the emulator.** If it ever appears
  to, check for a stale `hardware-qemu.ini.lock` **directory** left in the AVD folder —
  note the trailing item is a directory, so `Remove-Item` and `File.Delete` both fail on
  it, and `[System.IO.Directory]::Delete(path, true)` is what removes it. Do not spend
  time on `-no-snapshot-load` / `-wipe-data` / `-gpu swiftshader_indirect` first.

### 10.3 What Maestro sees is the view hierarchy, not the screen

Elements below the fold are not found. `tapOn` does not scroll.

- Call `inspect_screen` before targeting anything, and again after each UI change.
- For lists, use `scrollUntilVisible` rather than assuming an item is on screen.
- After `clearState: true` the scroll position is always the initial one, so the first
  interaction with a list needs an explicit `scrollUntilVisible`.

A "element not found" against an app that plainly shows it is usually this, not a bug.

- **Never begin a swipe near the screen edge.** A swipe starting around 95% of the
  width is the Android system back gesture: the app leaves the foreground and lands on
  the launcher, which then looks like an app crash. Start nearer the middle.

### 10.4 It verifies what it can see, and nothing more

Maestro proves a screen renders and responds to input. It does not prove a binding
resolved, that money was stored as kopecks, or that a transaction is atomic. Those stay
with the Release build (§1.1) and the `Tests` suite (§7).

### 10.5 Application exceptions are in a file, not in logcat

`logcat` does not carry this app's managed exceptions — the ones that matter most, such
as a `XamlParseException` raised while a page inflates. They go to a per-app log file:

```
adb -e shell "run-as com.companyname.cafeposapp tail -c 6000 files/logs/cafe-pos.log"
```

Reach for this the moment a page shows an error banner with no stack in logcat. The
banner text is the symptom; this file holds the exception. A first app start takes
**~8 seconds** (schema + seed + automatic backup) and shows a blank screen throughout —
that is initialisation, not a hang.

## 11. Comments: what stays in the code and what leaves it

The codebase went from 12 368 comment lines to 6 849. The prose now lives in 16 documents
under `docs/decisions/`; the code keeps a pointer. This section is the rule that decided
each of those, so the next pass does not have to re-derive it.

### 11.1 The rule

- **A one-line `/// <summary>` STAYS in the code.** It is the API surface — it is what a
  hover shows. One *line*, not one sentence.
- **`<remarks>`, and any `//` block past about two lines, MOVES to `docs/decisions/`.**
  The code keeps a pointer and nothing else:
  `/// <remarks>Why so — docs/decisions/catalog-management.md</remarks>`
- **Threshold by characters as well as lines: 220.** Both halves are needed. Three short
  lines are fine to read; one 300-character line is not, and counting lines alone would
  have waved it through. A five-line comment of 200 characters is harmless.
- **A `summary` over 220 characters is prose that happens to live inside a `<summary>`,
  so it moves too** — and the code keeps the **first sentence** only.
- **Misplaced `///` inside a method body becomes `//`.** `CS1587` only says "XML comment
  is not placed on a valid language element", which does not tell you where it should go.
- **A field and an enum member are declarations**, and their doc comments stay `///`:
  `private const char RussianTrunkPrefix = '8';`, `Unknown = 0,` and `Cheaper,` all get
  real documentation. Do not "fix" these into `//`.
- **Text moves VERBATIM.** Never retype it, never retranslate it, never improve it. Only
  the markup changes: `<see cref="X"/>` and `<c>X</c>` become backticked X, `<b>X</b>`
  becomes `**X**`, `<para>` becomes a blank line. **Documents stay English; the UI stays
  Russian.** A paraphrase is a different comment, and the original is what recorded the bug.

### 11.2 A trap belongs at the code; reasoning belongs in the document

Two different kinds of comment, two different places.

- A **trap** — "an unknown member in XAML aborts at inflation, not at build" — is one
  line and stays where the code is, because that is where you will be standing when you
  hit it.
- **Reasoning** — why this design rather than the obvious alternative, what was measured,
  what was rejected — is what moves. It is the part that goes stale and that nobody reads
  at the call site.

### 11.3 Group by subject, not by directory

One decision usually spans a service *and* the model behind it. `OrderService`'s rules and
`Order`'s own fields belong in one document; splitting them by folder puts half an
explanation in each and neither is readable. Current subjects: `orders`, `combos`,
`checkout`, `cash`, `stock`, `shared`, `schema`, plus one per UI area. `README.md` in
`docs/decisions/` is the index — **add to it when you add a document.**

### 11.4 Three ways this was done wrong, so that they are not done again

All three shipped, and all three passed a clean build first.

1. **Collapsing a multi-line `<summary>` onto one line.** It silently drops every
   `<see cref="X"/>` and leaves a sentence dangling where the reference was:
   `appended to <see cref="StatusText"/>, because…` became `appended to, because…`.
   **131 sites.** The tell is a sentence that no longer parses. **If a summary must be
   shortened, shorten it by hand and read the result** — never by regex.
2. **Writing multi-line content into a single `///` line.** An embedded newline leaves
   every continuation line without its marker, so the result is not a comment at all.
   This was **1 101 errors**. Collapse whitespace before splitting on the first sentence.
3. **Deciding by asking whether `<remarks>` exists.** A long `<summary>` with no
   `<remarks>` is still prose. Ask whether the *text* is long, not which tag holds it.

**When moving comments in bulk, verify afterwards rather than trusting the script:** count
what is left, confirm a few distinctive phrases are findable *somewhere* (code or
document), then build. `git checkout --` is the recovery from a bad scripted edit, and it
was needed three times.

### 11.5 XAML-bound types must stay at namespace level

A nested type cannot be named from XAML: `clr-namespace` has no syntax for it. The
`OrderTab` crash was exactly this. If a ViewModel has to be reachable from markup, it is a
top-level type in its own file.

## 12. Files: size, how to split, and who owns what

### 12.1 Size

**Limit: 500 lines per file. Test files are exempt** — a long test class is a
specification, and splitting it costs more than the line count saves.

Measured, current state — recorded honestly rather than gamed:

| File | Lines | |
|---|---|---|
| `Tests/CashReconciliationTests.cs` | 693 | exempt (test) |
| `Tests/CashLedgerTests.cs` | 533 | exempt (test) |
| `CafePos.Presentation/ViewModels/ShiftAnalyticsViewModel.cs` | 525 | one type, no prose left |
| `CafePos.Presentation/ViewModels/MenuViewModel.Methods.cs` | 502 | shell, §12.2 |

Two product files are over, both barely. The plan's substantive criterion — "no business
logic in the shell" — **is** met; the raw line count for `MenuViewModel` is not, and the
reason is written out in `docs/PLAN-architecture-debt.md` rather than hidden.

### 12.2 Split by duty, never by line range

- **The test: after the split, can you name each part in one sentence without the word
  "and"?** If the name needs "and", you cut in the wrong place. `MenuViewModel.Methods`
  (the shell) and `MenuViewModel.Load` (loading) are duties; "lines 1–500" is not.
- **Order the parts by dependency direction.** What knows about other things goes above;
  what only computes goes below. `OrderDetailsViewModel` → `.Commands` → `.Items` →
  `.Money` is one direction and reads top-down.
- **A `partial class` is the tool.** Same namespace, same `partial` keyword. Splitting by
  duty names the parts; splitting by line range only shortens files.
- **Never move an `await` across a class boundary unless the caller receives a named
  operation.** `Task DoThingAsync()` loses the name of what it did. The caller must get a
  value it can reason about.
- **Coordinators return outcomes; they do not clear the screen.** `CheckoutCoordinator`
  returns `SaleResult`/`SaleOutcome`, which is what keeps `FulfilmentEditor` and
  `DraftAutosave` out of its constructor and removes the need for `INavigationService`.
- **Constructor order is load-bearing when lambdas close over collaborators.** Build the
  collaborators *before* the subscriptions and commands — `MenuViewModel.Methods.cs`
  does, and reordering it is where `CS8602` came from.

### 12.3 Responsibility zones — enforced by the compiler, not by discipline

This is the part worth reading. These boundaries are real `ProjectReference` edges, so a
violation is a **build error**, which is the good kind of signal.

| Zone | Project | TFM | May reference | Cannot possibly use |
|---|---|---|---|---|
| Domain | `Core/` | `net10.0` | nothing — zero references | **any MAUI type at all**, not even `Color` |
| Presentation logic | `CafePos.Presentation/` | `net10.0` | `Core` | `Views`, `Converters`, app `Services` |
| UI + platform | `CafePosApp` — `Views`, `Controls`, `Converters`, `Services`, `MauiProgram` | `net10.0-android` + ios / maccatalyst / windows | both | domain logic: no arithmetic, no validation |
| Tests | `Tests/` | `net10.0` | `Core`, `CafePos.Presentation` | the MAUI project, at all |

**What that buys, stated as consequences:**

- **`Core` cannot use MAUI.** If a rule needs a `Color`, it is not a domain rule — move it
  down. `Core/Common` holds pure decision types with no dependencies: `BundlePlan`,
  `OrderPromise`, `FulfilmentSwitch`, `MenuFilter`, `PaymentBooking`, `CartStepDown`,
  `SaleOutcome`.
- **`CafePos.Presentation` can use `Microsoft.Maui.Graphics` and nothing else from MAUI.**
  That package *is* referenced, which is why `Color` works and `Application.Current`,
  `AppTheme`, `MainThread` and `Geometry` do not. §6's warning that "the type is rarely
  the one you would guess" is this same boundary, discovered the hard way.
- **A real collaborator lives in `CafePos.Presentation/ViewModels/`** — not in `Core`,
  not in `Views`: `CartBuilder` (zero dependencies, takes `Action<string> announce`),
  `FulfilmentEditor`, `CompositionResolver`, `DraftAutosave`, `CheckoutCoordinator`,
  `ParkedCarts`, `MenuCatalogue`.
- **`Tests` cannot see the UI layer.** That is why the application layer has no automated
  coverage and why the honest answer to "is this tested?" is often a device pass.
- **The dependency set of `CafePos.Presentation.csproj` is the design.** One reference and
  two packages. Do not grow it to make a problem go away.

## 13. How to build a chip

A chip is a rounded, single-line, tappable filter token. There is one correct way to make
one, and getting it wrong produces the specific visual failure recorded in §2.

**Always use the existing pair of styles. Never inline a chip.**

```xml
<ScrollView Orientation="Horizontal"
            HorizontalScrollBarVisibility="Never" VerticalScrollBarVisibility="Never">
    <HorizontalStackLayout BindableLayout.ItemsSource="{Binding CategoryFilters}"
                           BindableLayout.ItemTemplate="{StaticResource CategoryChipTemplate}"
                           Spacing="6" />
</ScrollView>
```

- **Container: `ScrollView` > `HorizontalStackLayout`.** Never `FlexLayout` — §2.
- **Height 44dp** — one notch under the 48dp floor and still a whole chip, which is §6's
  documented exception. **Corner radius = height ÷ 2**, so `RoundRectangle 22` on a
  `Border`, or `CornerRadius="20"` on a `Button`.
- **Padding `14,0`.** The vertical zero is deliberate; the height carries it.
- **`MinimumWidthRequest="64"`.** A chip is as wide as its label, so «Все» (three letters)
  came out 50×44 dp, and a 22 dp radius on that is a **circle** — it reads as a radio
  button parked next to real chips. 64 dp keeps every chip reading as a pill.
- **`MaxLines="1"` + `LineBreakMode="TailTruncation"` on the text.** On a `Label`
  (`FilterChipText`) both apply; on a `Button` (`SectionTab`) `MaxLines` is `XC0001` and
  only `LineBreakMode` does — §2.
- **Selection is never colour-only.** A filled pill *and* the filter actually taking
  effect (§6).
- **Decide scroll vs wrap with arithmetic, not taste.** Measure the chips and compare with
  the screen: five sections came to 75.8 + 69.3 + 80.8 + 122.3 + 114.7 = **463 dp** plus
  24 dp of gutter, on a **411 dp** emulator. Nothing fits → scroll. If it fits, do not add
  scrolling. Hardcode no width and keep no breakpoint: the same layout has to work at
  360 dp and on a tablet.
- **Verify by measurement, then by looking.** The defect was found with `uiautomator`
  bounds (§1.2) and confirmed by eye. A chip should measure the height it declares.

**A chip is not the place for a long name.** It truncates — and truncation is only
acceptable because **the full name is still reachable**: every chip template carries
`SemanticProperties.Description` with the untruncated name, as `SectionChipTemplate` does
with `StringFormat='Открыть раздел: {0}'`. A chip that truncates *without* that is a chip
whose name a screen reader cannot read. Verified with a 37-character category name: the
chip measured 252.6 × 42.3 dp, one line, and the list row below carries the full name too.

## 14. Graphics: icons, colour, fonts, and what not to assume

**Icons are glyphs in a `Label`** — not images, not path geometry. That is the whole
mechanism here, and it has three sharp edges.

- **The glyph must be covered by the bundled font.** Only two are registered,
  `<MauiFont Include="Resources\Fonts\*">` → `OpenSans-Regular.ttf` and
  `OpenSans-Semibold.ttf`. **U+2713 ✓ is not in OpenSans** and renders as tofu, so the
  success check is **U+221A √**. Check the glyph in the font, not in your head.
- **Emoji-presentation characters have no monochrome outline and collapse into solid
  blocks.** `📋 🕐 📊` were all unreadable filled shapes on the tab bar; `☰ 📂 ⚙` are
  covered and render as real outlines. **Check a new glyph on the tab bar itself**, where
  it renders differently from inside a sheet.
- **`shapes:Path.Data` cannot be bound.** Only a *literal* attribute goes through the
  `Geometry` TypeConverter; a `Binding` hands the value straight to the property, so a
  converter returning a path string throws `InvalidCastException`. Use a literal `Data`
  or a glyph.

**Colour.** All of it lives in `Resources/Styles/Colors.xaml` under semantic names —
`Primary`, `Success`, `Danger`, plus `Gray` scales. **Never a hex literal in a page.**
Anything that must change between light and dark uses `AppThemeBinding`; a hardcoded
colour is a bug in dark mode, not a shortcut. Feedback is never colour-only (§6).

**Styles.** `Resources/Styles/Styles.xaml` holds 42 keys, semantically named — `RowTitle`,
`RowPrice`, `FilterChip`, `SectionTab`, `CountLabel`, `CardBorder`. **Find the existing
style before inventing one:** a new style is a decision belonging to the design system,
not to one page. Size and colour pair up inside one style, so a chip is two style
references and no inline numbers.

**Do not assume an asset is wired.** `Resources/Images` holds ten `.svg` files that
**nothing in the XAML references** — they are design sources, as are `Resources/AppIcon`
and `Resources/Splash`. Only what appears as a `StaticResource`, `MauiFont`, `MauiImage`
or `AppIcon` is real.

## 15. Tooling traps that have cost real time

Not MAUI, not domain — just this environment, written down once.

- **Verify non-ASCII text by codepoint, never by console output.** PowerShell renders
  Russian as mojibake whatever the file says. A whole debugging pass went into proving a
  string that was already correct.
- **`$` in a PowerShell double-quoted string must be escaped**; inside a single-quoted
  heredoc it is literal — which is how a `$Source` header line silently went missing.
- **`-replace` with a `$` anchor needs `\r?$` in multiline mode.**
- **A per-file "characters lost" report is usually text that merely moved.** Compare
  against the combined new files before believing a loss.
- **Long scripted edits go wrong silently.** Short commands, plus `edit` and `read`, were
  noticeably more reliable than one long PowerShell script. Build after every batch, not
  once at the end.
- **Line-range surgery is unsafe.** Two blocks once began *after* their own doc comments
  and would have been dropped without the build complaining. Verify coverage before
  splitting, and read the result.
- **A moving line number in a build error is a parser giving up,** not a shifting fault.
- **Characterisation tests earn their keep here:** the 11 in `MenuCartTests.cs` have
  caught three real money and state bugs, and cost no expectation edits.

## 16. A change record per feature or fix

**Every feature and every fix gets its own file in `docs/changes/`, stamped with the time,
recording what we are doing.** The template, the naming rule and the full rationale are in
[`docs/changes/README.md`](../docs/changes/README.md); this section is the part an agent
has to follow.

- **Create it before the first code change**, on the branch, in the same commit. Its value
  is that it captures intent while intent is still cheap to change.
- **Add a row to `docs/changes/CHANGELOG.md` in that same commit.** One index for the
  whole history: what we did, and which file holds the detail. It is what turns
  `docs/changes/` from a pile of files into something searchable — one table answers both
  questions instead of a directory listing and a guess at file names. **Append one row;
  never rewrite the table**, so the diff shows one change. Fill the `Merged` column with
  the merge commit, `—` before that.
- **The index and the files beside it must agree.** A record on `develop` with no row in
  `CHANGELOG.md` means the index is wrong. An index that looks authoritative and is not is
  worse than no index, which is why this is not optional bookkeeping.
- **Name it `YYYY-MM-DD-HHMM-<slug>.md`,** local time, 24-hour, zero-padded. The stamp
  sorts chronologically and cannot collide — several changes get started in one session.
- **Commit it.** These are history, not scratch. An abandoned attempt stays with
  `Status: abandoned` and says why: *how something was tried and rejected is worth more
  than a silence.*
- **It is not `docs/decisions/`.** A change record says *what changed and when*, keyed by
  date. A decision document says *why this design rather than the obvious alternative*,
  keyed by subject. Link to each other; never merge them.
- **Numbers, not adjectives.** `44.2 dp, measured from a uiautomator dump` is a record.
  `chips look right now` is not — and it is exactly the sentence §1.2 exists to prevent.
- On merge: set `Status: merged`, add the merge commit hash.

## 17. Planning writes back into these rules

**These rules are not a document that was written once. Every planning session ends by
amending them.** A decision taken in planning and not recorded here gets re-litigated next
month, or — worse — silently contradicted by the next agent, because the rule and the
decision now disagree and only one of them is visible.

### 17.1 `grill-me` before a new feature or a fix

**Load the `grill-me` skill before starting any new feature or fix.** Its job is to
interview the owner thoroughly enough that the work cannot go the wrong way for a reason
nobody thought about. The owner asked for this explicitly: the questions are cheaper now
than the rework is later.

```
skill: grill-me
```

- **Run it before the first code change**, not once the shape is already decided. An
  interview after the implementation confirms decisions; an interview before it makes them.
- **Its questions outrank your own plan.** If you had a design in mind and `grill-me`
  contradicts it, the answer is to change the design.
- **This applies to any planning skill, not only `grill-me`.** `planning-with-users`,
  `writing-plans`, `brainstorming` — whatever produced the decision, the write-back
  obligation in §17.2 is the same.

**One carve-out, flagged rather than assumed:** a truly trivial change — a typo, a
one-character fix with an obvious cause — does not need an interview, and a rule that is
routinely overridden is worse than a small control (§6). *The owner may overrule this.*
Nothing else is carved out: anything touching money, stock, an order's state, or a layout
gets interviewed whatever its size.

### 17.2 The write-back obligation

When planning produces a decision, one of these is true before the merge (§3.3 item 5):

1. **A new rule** → add it to the section that owns the subject, and say so in the change
   record's *Rules this changed*.
2. **An existing rule is now wrong** → **amend or remove it.** Leaving a rule in place
   that the accepted decision contradicts is the failure this section exists to prevent.
   A stale rule is not neutral: it is an instruction to do the thing you just decided
   against.
3. **The decision is specific to this change** → it belongs in
   `docs/decisions/<subject>.md` and in the change record, and **not** in these rules.
   These rules carry what must be true every time; that carries what was true once.

**Where each kind of rule goes** — put it where a reader would look for it:

| Kind of rule | Goes in |
|---|---|
| How to do something here (comments, chips, graphics, splitting) | §11–§14 |
| A MAUI or tooling trap that cost real time | §2 or §15 |
| A measurement or verification obligation | §1 |
| Something that must never be done | the section that owns the subject |
| A product rule | §5 or §6 |
| A one-off decision | `docs/decisions/`, not here |

**Then add the index line.** A new `docs/decisions/` document goes into that folder's
`README.md` (§11.3); a new rule that points at a document must name a document that
exists.

### 17.3 The loop, in one line

**`grill-me` → decide → `docs/changes/` → code → measure → write back into this file →
merge.** The write-back is not optional bookkeeping; it is the step that makes the next
change cheaper, and skipping it is how this file started to contradict the codebase.
