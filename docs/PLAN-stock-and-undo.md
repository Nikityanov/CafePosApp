# План: склад при правке заказа и отмена ошибок

Семь веток, отобранных из десяти предложенных улучшений интервью 2026-10-07. Порядок жёсткий
и обоснованный: **значок «осталось N порций» ставится на числе, которое перестаёт быть
правдой после первой же правки заказа**, поэтому склад чинится первым, а не рядом.

Все утверждения о коде — прочитаны и проверены grep'ом по строкам; номера строк указаны там,
где именно утверждение важно.

---

## 1. Что умерло и почему

Четыре из десяти не выжили интервью. Это результат, а не побочный эффект.

| Идея | Почему не делаем |
|---|---|
| Печать чека (ESC/POS) | Владелец: «ничего из перечисленного» — ни термопринтера, ни сканера, ни второго устройства. Задачи нет |
| Округление итога и сдача | Правило владельца: деньги — «только с причиной и автором». Округление это правило без причины, оно под это правило не подводится |
| Быстрый повтор заказа | Не болело. Отложено, не отменено |
| Сравнительная аналитика (дельта к прошлой смене, пик по часам) | Не болело. Отложено |

Печать — единственная идея, которая не может вернуться без нового железа.

## 2. Три находки, которые переписали план

### 2.1. Правка заказа не пишет списание **и не проверяет наличие**

`Core/Services/OrderService.Commands.cs:221` `UpdateOrderAsync` добавляет и убирает строки.
Движений склада в методе нет: `StockMovement` пишется ровно в двух местах продакшн-кода —
`Core/Services/CheckoutService.cs:149` (списание) и `Core/Services/InventoryService.cs:54`
(поставка). Это не дыра в запасе, а отсутствие механизма.

Две дыры, вторая хуже первой:

- **Списания нет.** Добавил позицию — ингредиенты не сошли. Убрал позицию — остались списаны,
  хотя их не варили.
- **Проверки наличия нет.** В готовый заказ можно вписать позицию, ингредиентов для которой
  уже нет, и приложение не скажет ни слова. `CheckoutService.cs:96` бросает
  `InsufficientStockException`; на пути правки такой проверки не существует. Проверка рецептов
  (`WarnAboutMissingRecipesAsync`) тоже только на чекауте.

Последствие, которое делает дефект не тихим, а накопительным: возврат при отмене читает
журнал, а не рецепт — это зафиксировано тестом
`The_stock_reversal_returns_what_was_written_off_not_what_the_recipe_says_now`. Значит как
только заказ правят, журнал навсегда расходится с заказом, и отмена возвращает не то:

- капучино ×2 → ×1: вернётся молоко за **две** чашки, одна выпита;
- капучино ×1 → капучино ×1 + эспрессо: не вернётся **ничего**.

Владелец: правят изредка. Значит дефект не пожар, а тихий счётчик, который заврёт.

### 2.2. «Отмена отложенного чека» стирает два объекта

`DraftOrderService.TakeAsync` (`Core/Services/DraftOrderService.cs:113`) делает
`db.DraftOrders.Remove(draft)` и сохраняет. Загруженный отложенный чек **удаляется из базы**.
Плюс `ParkedCarts.OpenAsync` (`CafePos.Presentation/ViewModels/ParkedCarts.cs:111`) делает
`cart.Cart.Clear()` — чек, который был на экране, остаётся только в памяти и тоже пропадает.

Отмена тут — это два сериализованных снимка и обратная запись в базу, то есть отмена, которая
сама может потерять данные. Дешевле не дать потерять: отказаться грузить поверх непустой
корзины («сначала отложите текущий» — `ParkAsync` уже есть и сам спросит имя) либо откладывать
текущий автоматически. Оба делают потерю невозможной вместо отмены задним числом. Это правка
поведения, а не стека, и она идёт **до** отмены, а не вместе с ней.

### 2.3. Значку порций нужен запрос, которого нет

`MenuCatalogue.LoadAsync` (`CafePos.Presentation/ViewModels/MenuCatalogue.cs:95`) грузит
продукты и категории. Рецепты не грузит нигде на странице меню. Значок — это плюс один запрос
на самый горячий экран приложения.

Вторая часть: `RecipeItem` висит только на `Product` (`Core/Models/RecipeItem.cs`), у `Combo`
рецепта нет. Комбо раскрывается в составляющие через `ComboExpander.Expand`, поэтому склад оно
списывает честно — но компонент комбо **без рецепта** продаётся с предупреждением
(`CheckoutService.cs:201`), и для него количество порций **неизвестно, а не ноль**. «0 порций»
на такой плитке — враньё привычным.

## 3. Решения владельца

Интервью `grill-me`, 2026-10-07, четыре раунда.

| Вопрос | Ответ |
|---|---|
| Что откатываем | Все четыре вида: статус заказа, отложенный чек, движение по кассе, факт оформления |
| Сколько живёт отмена | Стек на всю смену |
| Отмена денег | Ведёт в существующий отказ с причиной. Деньги сторнируются, не стираются |
| Отмена оформления | Только пока заказ «В работе» |
| Глубина отмены | Одно действие. Отмена отмены запрещена |
| Автор | Один оператор на смену |
| Где сигнал о нехватке | Плитка блюда: число порций, с учётом корзины |
| На нуле порций | Серая плитка, остаётся на экране и говорит почему |
| Порядок работ | Сначала дефект склада |
| Правка заказа | Отказывать, если ингредиентов нет |

## 4. Ветки

Каждая — `docs/changes/` запись до первой строки кода, ветка от `develop`, merge обратно.

### 1. `fix/order-edit-stock` — дефект учёта

**Правит две дыры из §2.1.** Списание симметрично, проверка наличия обязательна.

Принятые решения:

- **Решение выносится в `Core/Common`** (`StockDeltaPlan`), как `BundlePlan` и остальные 22
  чистых типа: пересчитать спрос до и после, отдать знаки дельт и тексты.
- **Проверка наличия до записи**, как на чекауте: нехватка отказывает всю правку, а не
  половину её.
- **Движения пишутся только за вычетом из порции, а не по факту наличия на полке.**

Ожидаемый вид журнала после правки «капучино ×2 → ×1» при 100 000 мл молока:

| Строка | Δ | Reason |
|---|---|---|
| чекаут ×2 | −400 | `Заказ #1` |
| правка 2 → 1 | +200 | `Правка заказа #1` |
| отмена с возвратом | −200 | `Возврат по заказу #1` |

Итог: полка вернулась к 100 000, журнал сошёлся, всё видно.

- **Столкновение, которое придётся разрешить в этой же ветке.**
  `StockPlan.ReverseAsync` (`Core/Services/StockPlanner.cs:79`) отказывается возвращать склад,
  если у заказа есть **любое положительное** движение с `OrderId`. Правило появилось, когда
  положительных движений с `OrderId` не существовало вовсе. Строка правки может быть
  положительной, поэтому праило надо сузить до «поступление на склад», а не «любое
  положительное». Решение: **типизированная причина движения**, а не разбор строки `Reason` —
  по той же причине, по которой деньги это `INTEGER`, а не `TEXT` (§5): сравнение по строке
  ломается, а читатель не видит, что сломалось.
- **Что НЕ делаем в этой ветке:** значок на плитке, отмена, скидка, оператор.

### 2. `feat/menu-tile-portions` — число порций на плитке

Арифметика: `min` по рецепту из `floor(остаток / расход на порцию)`. Округление вниз —
обещать нельзя то, что не нальёшь. Учитывает корзину (решено владельцем), то есть
пересчёт на каждое изменение корзины.

Три состояния плитки, и «неизвестно» — третье, а не «ноль»:

| Состояние | Показ |
|---|---|
| Хватает с запасом | Как сейчас, без значка |
| Порти впритык | Число порций |
| Ноль | Серая плитка с причиной |
| Рецепта нет | **Неизвестно.** Не ноль |

Правило «недоступное показывается состоянием, а не действием» (§6) уже есть для часовых окон
— это его распространение на склад.

### 3. `feat/parked-cart-not-destructive` — не дать потерять (§2.2)

Прежде любой отмены отложенного чека. Либо отказ грузить поверх непустой корзины, либо
автооткладывание.

### 4. `feat/undo-status` — отмена статуса

Самый дешёвый вид: без денег, без склада, один переход назад.

### 5. `feat/shift-operator` — имя оператора на смену

Разблокирует «автора», без которого не начинаются ни деньги, ни скидка. Схема: имя на `Shift`.

### 6. `feat/undo-money-and-checkout` — деньги и оформление

Ведёт в **существующий** отказ с причиной. Стек не изобретает второй механизм, он предлагает
путь.

### 7. `feat/manual-discount` — скидка с причиной

Секция скидок в отчёте уже есть (`GetDiscountedLinesAsync`) и наполняться нечем. Оператор
не может скинуть цену ни на одну позицию.
