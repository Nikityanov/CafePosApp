Документ — единственный источник правды для этой фичи. Решения приняты после опроса

## 1. Комбо

### 1.1 Что подтверждено практикой

- **Ключевая ось — не «composite vs modifier», а идентичность компонента.** Компонент
  обязан быть настоящим товаром со своим складом, своим 86 и своим отчётом. Иначе
  инвентарь не списывается. Выбранная нами схема (компоненты = `Product`) — это
  большинство: Square, Simphony, Lightspeed, D365 («components are the truth, parent is a
  rollup»).
- **Вложенных комбо не существует ни у кого.** Shopify: «Nested bundles aren't supported».
  Deliverect — то же. D365 обходит перечислением, что даёт комбинаторный взрыв
  (у Simphony из-за этого нельзя копировать группы). Наш выбор «без вложенности» — верный.
- **Количество N = N одинаковых наборов** — единогласно. Кратность компонента живёт в
  слоте (`QuantityPerUnit`), а не выводится из количества строки.
- **Цена = сумма компонентов** — подтверждено (Simphony option 4 «Add Side Prices To Meal
  Price» по умолчанию), и **мы это сознательно НЕ выбрали**; см. §1.3. У Simphony есть и вторая
  опция — цена задаётся в карточке позиции, — и выбрана вторая. Обе документированы, и вопрос
  был не в том, какая модель верна, а в том, кто владеет решением.
- **Цена в комбо заменяет цену блюда, а не добавляет** — Aloha price method «Item price».
  У нас уже `ProductAddFlow.ResolvePrice` делает «заменяет», поэтому вариант в слоте
  добавляем без новой архитектуры.
- **86'd компонент: никто не удаляет и не выкидывает молча — подменяют.** Simphony
  substitution groups, D365 product substitutes. Отсюда решение: подмена, а не блокировка
  продажи. Пересчёт цены на замену — **часть решения тех платформ, но не нашего** (см. §1.3):
  при фиксированной цене комбо разницу поглощает кафе.

### 1.2 Сущности

```
Combo                       — шаблон в каталоге. БЕЗ ЦЕНЫ.
  Id, Name (160), IsDeleted, SortOrder

ComboComponent              — слот шаблона.
  Id, ComboId (FK, cascade)
  ProductId (FK, Restrict)          — настоящий Product, не option
  QuantityPerUnit (int >= 1)
  ComponentPriceKopecks (long?)     — null = цена блюда; 0 = бесплатно; число = своя
  SubstituteProductId (Guid?)       — чем заменить, если основной 86нут

OrderItemComponent          — снапшот состава на момент продажи.
  Id, OrderItemId (FK, cascade)
  ProductId
  ProductName (160)                — снапшот имени
  QuantityPerUnit (int)
  UnitPriceKopecks (long)          — сколько берём в комбо (Price/Prep Cost из Simphony)
  ReferencePriceKopecks (long)     — à la carte цена того же блюда; для «было/стало»
  SortOrder (int)

DraftOrderItemComponent     — зеркало для отложенных чеков.
  то же, но DraftOrderItemId
```

`ReferencePriceKopecks` — обязателен. Simphony хранит `Price` и `Prep Cost` рядом именно
поэтому, что из одной транзакции должны строиться оба отчёта: «сколько продали комбо» и
«сколько это стоило по отдельности». Без второго поля скидку на комбо нельзя ни показать,
ни потом отчетить.

### 1.3 Ценообразование

Новый файл `Core/Common/ComboPricing.cs`. Точные имена членов — по коду; здесь решение, а не
сигнатура.

```csharp
public sealed record ComboComponentPrice(int QuantityPerUnit, long UnitKopecks)
{
    public long LineKopecks => (long)QuantityPerUnit * UnitKopecks;
}

public static class ComboPricing
{
    // Сумма компонентов ПО А ЛА КАРТЕ. Это ОРИЕНТИР, а не цена.
    public static long ReferenceKopecks(IEnumerable<ComboComponentPrice> components);

    // Насколько комбо дешевле суммы своих частей. Возвращает null, а не делит на ноль.
    public static decimal? DiscountPercent(long referenceKopecks, long priceKopecks);

    public static long ResolveUnitKopecks(long? componentPriceKopecks, long productPriceKopecks);
}
```

Инвариант: **у `Combo` есть собственная цена `PriceKopecks`.** Это то, что касса берёт.
Сумма компонентов — **ориентир**, относительно которого считается скидка, и она никак на цену
не влияет.

> **РЕШЕНИЕ ИЗМЕНЕНО 2026-10-05.** Первоначально цена комбо вычислялась как сумма
> компонентов и менялась автоматически. Владелец это решение перевернул, и на то есть
> основание: в Oracle Simphony это документированная альтернатива «Add Side Prices To Meal
> Price» — цена задаётся в карточке позиции и за частями не следует. Причина не в
> удобстве, а в **владении решением**: цену и скидку определяет бухгалтерия, программа
> записывает, а не вычисляет.

Следствия, которые обязаны выполняться:

- Смена цены компонента **не** переоценивает комбо. Комбо может оказаться дороже суммы
  частей — это наценка, и она разрешена. Подписывать надо честно («наценка 5%»), а не
  молчаливой «скидкой −5%».
- **Подмена компонента не двигает цену.** Раньше недоступный компонент с доступной заменой
  добавлял разницу в счёт (поведение D365). При фиксированной цене комбо разницу поглощает
  кафе, а не клиент. Замена всё равно пишется в снапшот строки — кухне и последующей
  проверке нужно знать, что фактически подали.
- Слот с ценой `0` влияет **только на ориентир**. Он больше не делает часть комбо бесплатной
  для клиента.
- `SaveComboAsync` отказывает в цене `<= 0`: товар по нулевой цене — ошибка данных, а не
  выгодное предложение.

Инвариант заказа сохраняется: `Order.RecalculateTotal` = `Σ(PriceKopecks × Quantity)`.
Комбо — одна строка, `PriceKopecks` = своя цена комбо. Тесты `MoneyTests.cs:44` и
`CheckoutFlowTests.cs:132` не ломаются. Миграция **012** добавляет `Combos.PriceKopecks` с
бэкфиллой, равной сумме компонентов: у существовавших комбо цена фактически и была этой
суммой, поэтому сумма — правда, а не догадка.

### 1.5 Списание ингредиентов

`StockPlanner.BuildAsync` принимает только `(ProductId, Quantity)`. Компоненты туда не
попадают. Решение — **не строить новый движок списания** (Toast Recipes и Restaurant365
считают себестоимость аналитически, реального списания по ингредиентам на компонент нет ни
у кого), а развернуть комбо до `(ProductId, Quantity)` на входе существующего планировщика.

Новый `Core/Common/ComboExpander.cs`:

```csharp
public static class ComboExpander
{
    // CheckoutLine -> пары (ProductId, Quantity) для StockPlanner
    public static List<ProductDemand> Expand(IEnumerable<CheckoutLine> lines);
    // Ингредиенты без рецепта среди компонентов — предупреждение, не запрет
    public static IReadOnlyList<string> DescribeComponentsWithoutRecipe(...);
}
public sealed record ProductDemand(Guid ProductId, int Quantity, string Name);
```

Предупреждение о блюдах без рецепта — требование пользователя и подтверждено практикой:
Toast ведёт 86-отчёт, но молчаливый пропуск рецепта приводит к тихому разъезду склада.
Предупреждаем, не запрещаем.

**Известное ограничение, фиксируется в коде как комментарий и в отчёте:** ингредиент,
который продаётся и сам по себе, и входит в два комбо, «тихо разъезжается» (документировано
в Shopify Community). Формула верна, но инвариант «сколько полных наборов можно собрать
сейчас» не поддерживается — это отдельная задача.

### 1.6 Недоступный компонент

1. Есть `SubstituteProductId` и substitute доступен → подставляем его, `UnitPriceKopecks`
   пересчитывается по его цене **только для ориентира и для снапшота строки** (чтобы кухня
   и последующая проверка видели, что фактически подали). **Цена, которую берёт касса, не
   двигается** — она у комбо своя, и разницу поглощает кафе, а не клиент. Это отличие от
   D365 («если замена дороже, цена кита пересчитывается») и сделано намеренно.
2. Substitute нет или он тоже недоступен → **продажа блокируется** с сообщением,
   называющим блюдо.
3. Компонент — бесплатный (`ComponentPriceKopecks = 0`) → влияет только на ориентир, то
   есть на отображаемый процент скидки. На цену и на возможность продажи не влияет.

Исторические чеки не ломаются: состав — снапшот имён и цен, `ProductId` в снапшоте не
используется для пересчёта.

### 1.7 Слот комбо собирается как строка корзины

Правило владельца: комбо собирается так же, как собирается заказ, с единственным
отличием — цену за всё комбо оператор задаёт сам. Поэтому слот — это строка корзины:
блюдо, количество, вклад в «по отдельности», удаление.

**Две строки, и это вынужденно, а не выбрано:**

| строка | что |
|---|---|
| 1 | `Picker` блюда, во всю ширину карточки |
| 2 | «2 × 160.00 ₿» + степпер `− N +` + `×` |

Пикер не может делить строку с другим контролом: нативный `Spinner` меряется шире своей
колонки `*`, его нативная цель касания перекрывает то, что справа, и накрытый контрол
рисуется на месте, но не отвечает (см. правило в `.opencode-rules.md`).

Убрано по решению владельца: поле количества с подписью «1 × 220,00 ₿ = 220,00 ₿»
(заменено степпером, в который нельзя вписать бессмыслицу), отдельная строка «Цена
блюда» (то же самое, что показывает вклад), выбор способа считать цену, поле своей
цены и подстановка. **Значения последних трёх по-прежнему записываются при сохранении**
(`ComboFormViewModel.BuildSlots`) — сохранение заменяет состав целиком, и форма,
перестав их показывать, стёрла бы их из карточки.

Команды степпера живут на форме, а не на строке: `StepComponentQuantityCommand` /
`StepComponentQuantityDownCommand`, строка приходит в `CommandParameter` — так же, как
в корзине. Единица — нижняя граница: `−` на единице отказывает, а не зажимает.

## 2. Время заказа

### 2.1 Что подтверждено практикой

- **ASAP-флаг не нужен.** Toast формулирует это как Lead time:
  `prep time = quote time + lead time`. Наш `RequestedAt == null` = ASAP, а обещание
  считается как `CreatedAt + LeadTimeMinutes`. Без lead time поле действительно ничего не
  сортирует — это была ошибка исходной постановки.
- **Обещание управляет воротами выпуска, а не позицией в очереди.** Toast: заказ на
  будущее лежит в «Pending Orders → Future Checks» и «appears as a preview ticket until
  the fire time is met». DoorDash: «Scheduled orders move to the Active tab based on the
  pickup time». То же у Square. Это принципиально иная форма, чем сортировка всего
  вместе.
- **Просроченное время — состояние отображения, а не ошибка валидации.** «No system found
  rejects an order whose promised time has simply elapsed while it sits in the queue.»
- **Два независимых таймера.** В реальных KDS цвет предупреждения мерит возраст с момента
  постановки в работу, а очередь — по обещанию. Смешивать нельзя.
- **`requested` и `promised` — разные поля** (Oracle Communications OSM держит
  `RequestedDate` и `Promise Date` раздельно, иначе при расхождении непонятно, кто врёт).
- **Клиенту — диапазон, не точка.** Management Science 71(9), 2025, 8 пререгистрируемых
  экспериментов, N=5323: диапазон нравится больше точной оценки, даже когда точная взята
  по верхней границе диапазона. Слишком широкий диапазон — хуже точного времени.

### 2.2 Модель

```
OrderType       { CounterService, Takeaway }   // TEXT, максимум 30
RequestedAt     DateTimeOffset?                // что попросил клиент; null = ASAP
```

Производное, не хранится:

```
IsScheduled      => RequestedAt.HasValue && RequestedAt > now
PromisedAt       => RequestedAt ?? CreatedAt.AddMinutes(LeadTimeMinutes)
IsOverdue        => PromisedAt < now          // для заказов в работе
```

`LeadTimeMinutes` — настройка, значение по умолчанию **10**. Хранится в существующей
таблице настроек, если она есть; иначе константа в `DatabaseOptions`. Не вводим новую
таблицу настроек ради одного числа.

### 2.3 Очередь

`OrdersViewModel` разбивается на три секции, существующие фильтры сохраняются:

| Секция | Условие | Порядок |
|---|---|---|
| **Срочные** | в работе и `PromisedAt < now` | по `PromisedAt`, затем `CreatedAt` |
| **В работе** | в работе, не просрочен, `RequestedAt` не в будущем | по `PromisedAt`, затем `CreatedAt` |
| **По времени** | `IsScheduled` | по `RequestedAt` |

Сортировка **в памяти**: SQLite не умеет `ORDER BY` по `DateTimeOffset`, и проект уже
так сортирует `CreatedAt`. Не вводим параллельную сортируемую колонку.

Колонка `Orders.RequestedAt` индексируется в миграции — индекс бесполезен без SQL-сортировки,
но нужен выборке по расписанию и делает возможным переход на неё позже без новой миграции.

## 3. Контакты

### 3.1 Что подтверждено практикой

- **Телефон привязан к типу заказа, а не является безусловной колонкой.** Toast привязывает
  запрос к поведению «Takeout»; Aloha — «an order for customer pick-up prompts for a customer
  phone number», а walk-in — отдельный режим; FireFly — переключатель «Full Lookup / Name
  Only / Phone Only / (none)»; Square — выключено по умолчанию; Frontol 6 — только для SMS
  фискального чека.
- **Free text хуже, чем кажется.** Frontol 6: «При вводе проверяется корректность номера»,
  затем — «необходимо еще раз проверить корректность данных **вместе с клиентом**, и
  подтвердить или изменить номер». Одна проверка ловит опечатки, вторая снимает вопрос
  подглядывания, и обе вместе дают «клиент не ищет в блокноте».
- **Хранить в E.164.** E.164 — формат хранения и передачи (`+`, код страны, до 15 цифр).
  E.123 — формат показа. Нормализовать дёшево сейчас, дорого потом.
- **Маскировать на клиентском экране.** PCI DSS 3.4.1 — до шести первых и четырёх последних,
  не больше. Наш клиентский экран — корзина на `MenuPage`; `OrderDetailsPage` служебный.
- **Телефон из заказа ≠ согласие на рассылку.** Square: ввод телефона не подписывает на SMS.
  У нас рассылок нет; фиксируем, что поле не создаёт согласия.

### 3.2 Поле

`Order.CustomerPhone` (TEXT, 24, nullable).

**Сохраняется только при `OrderType == Takeaway`.** Для `CounterService` значение
отбрасывается на границе сервиса и не пишется в базу. Это самое сильное сокращение объёма
данных: КоАП 13.11 ч.12 даёт 3–5 млн ₽ за неправомерную передачу по 1 000–10 000
субъектам, и счётчик — количество строк, а не сам факт колонки.

### 3.3 Нормализация

Новый `Core/Common/PhoneNumber.cs`. Без внешней зависимости — libphonenumber требует
восстановления пакета и тяжёл для одного поля.

```csharp
public static class PhoneNumber
{
    public static string? Normalize(string? raw);       // -> "+79XXXXXXXXX" | null
    public static bool IsValid(string? normalized);
    public static string Mask(string normalized);       // "+7 ••• ••• •• 42"
}
```

Правила: обрезать пробелы/скобки/тире/точки; `8` в начале → `7`; `9` в начале без кода
→ `+79`; цифры без `+` → `+7`; иначе если уже `+` — оставить; отбросить пустое; результат
не длиннее 15 цифр → иначе `null`. Возвращать `null`, а не бросать: пустой телефон — это
нормальное состояние.

Отклонённые символы внутри номера — признак опечатки, а не повод писать мусор в базу.

### 3.4 Удаление

`IContactDataService.PurgeAsync(TimeSpan olderThan)` обнуляет `CustomerPhone` у завершённых
заказов старше порога. Вызывается из закрытия смены. Порог по умолчанию **90 дней**.

Бэкапы: остаются на устройстве, ротация с ограничением числа файлов. Если текущий код
копирует без ограничения — ограничить.

## 4. Контроль цены

### 4.1 Что подтверждено практикой

- **Ни один стандарт этого не требует.** В PCI DSS v4.0.1 (397 страниц) слово «discount» —
  0 вхождений, «price» — 0, «pricing» — 0. Аргумент «так требует стандарт» непригоден.
- **Но состояние «любой, без PIN, без следа» ниже стартовой отгрузки вендоров.** Lightspeed
  по умолчанию даёт кассиру скидку до **100%**; Toast — «Any User»; Square имеет
  публично задокументированный обход и не даёт атрибуции по сотруднику без платного тарифа.
- **Аргумент — маржа, а не соответствие.** Median ресторан: 2,8% нетто от продаж. Скидка в
  1% продаж съедает ~36% прибыли.
- **Один путь записи цены — не контроль.** Квадрат показал обход: PIN на одной ветке, а
  другая ветка его обходит. Проверка обязана быть там, где проходит любое изменение.
- **Пересчёт «цена ≠ сумма компонентов» — наша инженерная идея, не опубликованная практика.**
  Не ссылаться на неё как на стандарт. Публикуемый аналог — before/after у Oracle, Bank of
  America, Bitta. Но «сложить компоненты обратно» — своё и полезное: ловит первое
  срабатывание без исторического порога.
- **Reason code вводить нельзя.** Причина на кассе превращается в первое выбранное значение;
  работает анализ паттернов.

### 4.2 Решение

`OrderItem.ListPriceKopecks` (INTEGER NOT NULL) — разрешённая из расчёта цена, неизменяемая.
`PriceKopecks` — фактически взимаемая, меняется при ручном пересмотре.

`PriceKopecks != ListPriceKopecks` = был ручной пересмотр. Работает для **любой** строки,
не только для комбо. Для комбо сверх этого работает `Σ(ReferencePriceKopecks)` — второй
независимый сигнал.

Отчёт смены получает раздел **«Скидки»**: строки с расхождением, с показом суммы скидки.
Это Tier-1 контроль (обнаружение) без единого секунды трения на кассе.

**Идентификатор оператора сознательно отложен.** Он требует сущности сотрудников, входа,
PIN, раздачи прав — это отдельная фича размером с эту работу. В плане фиксируется как
следующий шаг, потому что без него Tier-1 работает, но не говорит «кто».

**Порог вниз (Oracle E55)** — следующий шаг вместе с оператором: ограничение срабатывает
«only to prices that are lower than the item/offer price», то есть наценка порог никогда не
задевает.

Единственная точка контроля цены — `Core\Common\OrderLinePricing.Resolve`. Вызовов ровно
два: `CheckoutService.cs:155` и `OrderService.Commands.cs:231`. Это единственные два пути,
которые пишут цену строки, поэтому обходного пути нет — это был прямой вывод из
задокументированного обхода у Square.

### Что сделано

**Ядро.** `Combo`, `ComboComponent`, `OrderItemComponent`, `DraftOrderItemComponent`,
`OrderType`. `Migration010` и `Migration011` с явным созданием индексов и честной бэкфиллой.
`ComboPricing`, `OrderLineKey`, `ComboExpander`, `PhoneNumber`, `OrderLinePricing`.
`IComboService`, `IContactDataService`. `CheckoutService`, `StockPlanner`,
`OrderService`, отчёт скидок.

**Интерфейс.** Каталог комбо пятым разделом; редактор состава один на каталожное комбо и
кастомную сборку; пересмотр цены в корзине и в открытом заказе; тип заказа и телефон;
пикер времени (новый seam `IOrderTimePicker`); очередь тремя секциями; раздел «Скидки»
в отчёте по смене.

### Решения, принятые по ходу

1. **`ListPriceKopecks` не переписывается при правке существующей строки.** Разрешённая цена
   пишется один раз при создании строки. Переписывание уничтожило бы контроль: у строки без
   компонентов пересчёт вернул бы новую цену обратно в разрешённую, и пересмотр стал бы
   невидимым. Закреплено тестом
   `OrderLineMergeTests.Editing_a_line_keeps_its_identifier_and_its_allowed_price`.
2. **`ProductId` строки-комбо — это id шаблона `Combo`.** Обязательно для подстановки: замена
   является свойством слота каталога, поэтому сервер обязан найти шаблон. Строка с
   компонентами, чей `ProductId` не отвечает живому комбо, отклоняется с названием.
3. **`PhoneNumber.Normalize` понимает уже введённый код страны.** Правила плана дали бы из
   `79161234567` значение `+779161234567` — 13 цифр, которое проходит проверку на 15 и доходит
   до фискального чека нетелефонным. Добавлено правило: 11 цифр с ведущей `7` — код страны уже
   есть.
4. **`LeadTimeMinutes` — ambient static на `Order`**, назначается один раз при старте из
   `DatabaseOptions`. Сущность не имеет конструктора, куда его принять, а `PromisedAt`
   читается из разметки. Прецедент — `Currencies.Default`. Читается только при старте, поэтому
   обещание заказа не может пересчитаться задним числом.
5. **Повтор блюда в комбо запрещён в форме.** `ComboService` сопоставляет запрошенный
   компонент с *первым* слотом тем же `ProductId`, поэтому второй идентичный слот был бы
   недостижим, а не суммирующимся. Форма говорит «увеличьте количество».
6. **Отчёт о скидках включает отменённые заказы** и несёт `Status` каждой строки: отменённая
   продажа — самое интересное место для пересмотра цены, но её деньги возвращены, поэтому
   раздел не суммируется ни в какую выручку.
7. **`CatalogActions.ForCombo()` остался приватной статикой** в ViewModel, а не в Core, где
   лежат остальные пять меню. Обходные меню строятся в Core, чтобы их формулировки
   проверялись из тестового проекта. Стоит перенести при следующем касании того файла.

### Известные ограничения, зафиксированные намеренно

- Идентификатора оператора нет — см. раздел 4.2. Раздел «Скидки» отвечает на вопрос «сколько
  и на сколько», но не «кто». Это отдельная фича размером с текущую работу.
- Порога пересмотра вниз нет по той же причине.
- Комбо, оценённое правильно, но дешевле суммы частей, в раздел «Скидки» не попадает:
  фильтр — расхождение цены. Это вторая секция, которой план не просит.
- 15 расхождений индексов между свежей и обновлённой базой **предшествуют** этой работе
  (`Orders.Status`, `Products.IsDeleted`, `Shifts.IsActive`, `RecipeItems.*`). Не трогались.
- `PhoneNumber` нормализует под Россию. Для других стран нужна libphonenumber — сейчас её
  в проекте нет, а тянуть зависимость ради одного поля смысла не имеет.
- В `PreviewShortagesAsync` намеренно сохранена кортежная сигнатура, потому что её вызывает
  MAUI.

### Баг, найденный только запуском на эмуляторе

**Сборка и 362 теста были зелёными, а приложение падало при первом же добавлении блюда.**

```
XamlParseException: Position 204:67. Cannot assign property "IsEnabled":
Property does not exist, or is not assignable
  at ElementTemplate.CreateContent → TemplatedItemViewHolder.Bind
```

В `MenuPage.xaml` и `OrderDetailsPage.xaml` атрибут `IsEnabled="{Binding IsCombo}"` стоял на
`<TapGestureRecognizer>`. У распознавателя жеста **нет** свойства `IsEnabled` — оно есть
только у `VisualElement`, а `TapGestureRecognizer` им не является.

Почему это не поймали ни компилятор, ни тесты: падало **только при инстанцировании шаблона
строки корзины**, то есть в момент первого добавления позиции. До этого приложение
отрисовывалось нормально, потому что коллекция была пуста и шаблон не создавался.

Атрибут вдобавок был избыточен: родительский блок уже связан с
`IsVisible="{Binding IsCombo}"`, то есть для обычного блюда он целиком вне визуального
дерева, и распознаватель не может быть нажат в принципе.

**Вывод для процесса:** XAML-проверка сборки не покрывает свойства, которых нет у типа, если
шаблон ленивый. Единственная проверка, которая это поймала, — запуск на устройстве.
